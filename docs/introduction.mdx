TopK stores your documents in a collection, indexes the fields you choose, and retrieves them with vector search, keyword search, metadata filters, and custom ranking in a single query. TopK generates the embeddings, so semantic search works on plain text with no embedding pipeline on your side.

## What problem does TopK solve?

Retrieval for RAG, agents, and search products usually turns into a pipeline of separate systems that each hold a copy of your data. TopK replaces that pipeline with one collection and one query.

<CardGroup cols={2}>
  <Card title="The usual pipeline" icon="workflow">
    An embedding service, a vector database, a keyword engine for exact matches, a filter step, a reranker, and application code that merges the candidate lists. Every hop adds latency and a place for results to drift.
  </Card>
  <Card title="With TopK" icon="sparkles">
    One document carries a semantic index, a keyword index, dense or sparse vector indexes, and any metadata fields at once. One query scores against all of them, filters on any field, and ranks by an expression you write.
  </Card>
</CardGroup>

## What does a query look like?

Every TopK query has the same four stages, and the last one is where the name comes from. Here is a hybrid query over a collection of books. It combines a semantic score, a keyword score, and a metadata filter. The `client` object and the `books` collection are the ones created in the [quickstart](/quickstart):

<CodeGroup>

```python Python
from topk_sdk.query import select, field, fn, match

docs = client.collection("books").query(
    select(
        "title", "author", "rating",
        semantic_score=fn.semantic_similarity(
            "content", "a state that controls what its citizens think"
        ),
        keyword_score=fn.bm25_score(),
    )
    .filter(match("dystopian", field="genre"))
    .filter(field("rating") >= 4.0)
    .sort(
        field("semantic_score") * 0.7 + field("keyword_score") * 0.3,
        asc=False,
    )
    .limit(10)
)
```

```typescript JavaScript
import { select, field, fn, match } from "topk-js/query";

const docs = await client.collection("books").query(
  select({
    title: field("title"),
    author: field("author"),
    rating: field("rating"),
    semantic_score: fn.semanticSimilarity(
      "content", "a state that controls what its citizens think"
    ),
    keyword_score: fn.bm25Score(),
  })
    .filter(match("dystopian", { field: "genre" }))
    .filter(field("rating").gte(4.0))
    .sort(
      field("semantic_score").mul(0.7).add(field("keyword_score").mul(0.3)),
      false
    )
    .limit(10)
);
```

```sql SQL
SELECT
  title,
  author,
  rating,
  semantic_similarity(
    content, 'a state that controls what its citizens think'
  ) AS semantic_score,
  bm25_score() AS keyword_score
FROM books
WHERE match('dystopian', genre)
  AND rating >= 4.0
ORDER BY semantic_score * 0.7 + keyword_score * 0.3 DESC
LIMIT 10;
```

</CodeGroup>

<Steps>
  <Step title="Select" icon="list-checks">
    Choose the fields and scores to return. [`semantic_similarity`](/collections/query#semantic-similarity) embeds the query text with TopK's managed model and scores it against the semantic index on `content`. [`bm25_score`](/collections/query#bm25-score) reports how well each document matched the keyword filter.
  </Step>
  <Step title="Filter" icon="funnel">
    [`match`](/collections/query#keyword-search) requires the word "dystopian" in the keyword-indexed `genre` field, and the rating comparison reads a plain metadata field. Filters run before ranking, so every matching document is eligible for the result, no matter how selective the filter is.
  </Step>
  <Step title="Sort" icon="arrow-down-wide-narrow">
    Rank by ordinary arithmetic over fields and scores. Any [custom scoring](/concepts#custom-scoring) logic goes here instead of in a reranking step.
  </Step>
  <Step title="Limit" icon="trophy">
    Return the top *k* documents.
  </Step>
</Steps>

## What can you index?

A collection is a set of JSON-like documents with an `_id` field. You declare an index only for the fields you want to search on.

<CardGroup cols={2}>
  <Card title="Semantic index" icon="brain" href="/collections/manage#semantic-index">
    Managed embeddings over a text field. Query it with plain text.
  </Card>
  <Card title="Keyword index" icon="text-search" href="/collections/manage#keyword-index">
    BM25 full-text search with required and optional terms.
  </Card>
  <Card title="Vector index" icon="waypoints" href="/collections/manage#vector-index">
    Dense or sparse embeddings you bring, with cosine, euclidean, dot product, or hamming distance.
  </Card>
  <Card title="Multi-vector index" icon="layers" href="/collections/manage#multi-vector-index">
    Late-interaction models such as ColBERT, scored with MaxSim.
  </Card>
  <Card title="N-gram index" icon="regex" href="/collections/manage#ngram-index">
    Fast substring and regular expression filters on text.
  </Card>
  <Card title="Metadata fields" icon="tags" href="/collections/query#metadata-filtering">
    No index needed. Every other field is stored as is and can be selected, filtered, and used in scoring.
  </Card>
</CardGroup>

## How is TopK built?

<CardGroup cols={3}>
  <Card title="Object storage" icon="hard-drive">
    The only durable store. Billion-document collections at [10x lower cost](https://topk.io/benchmarks) than engines that keep everything in RAM.
  </Card>
  <Card title="Stateless compute" icon="server">
    Nodes cache in memory and on NVMe. Any node can fail or restart with no data loss and no consensus replication.
  </Card>
  <Card title="Reads apart from writes" icon="split">
    Separate node pools, so indexing and compaction never contend with your queries.
  </Card>
</CardGroup>

The [architecture](/architecture) page walks through the write path, the read path, and the query engine.
